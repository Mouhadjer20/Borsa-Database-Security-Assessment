# Project: Borsa — Educational Financial Web Application and Database Security Assessment

## 1. Project Overview

Develop a complete, functional full-stack web application named **Borsa**, designed as an educational financial platform for cybersecurity demonstrations, penetration testing exercises, and database security research.

Borsa simulates a fictional financial institution. Authenticated users can access their personal financial dashboards, view account information, and interact with a realistic financial environment using synthetic data.

The application serves two purposes:

1. **Functional financial application:** Provide a professional financial dashboard with authentication, user-specific accounts, account balances, and financial information.
2. **Cybersecurity research platform:** Provide a controlled environment for demonstrating, testing, measuring, and comparing common web application and database security vulnerabilities.

The primary security research scenarios are:

1. SQL Injection (SQLi).
2. Excessive Database Privileges.
3. Broken Authorization (BOLA/IDOR).
4. Database Network Exposure.

Additional research extensions include:

- PostgreSQL Row-Level Security (RLS).
- Authentication and session management weaknesses.
- Vulnerability chaining.
- Database auditing and security monitoring.
- Comparison of application-level and database-level security controls.
- Quantitative evaluation of security improvements.

**Important:** This project is exclusively for educational purposes and authorized security testing. All vulnerable implementations must operate exclusively inside the isolated laboratory using synthetic financial data.

If an expected table or column does not exist, report the missing dependency and document the required change separately. Never modify the database automatically.

The database administration and schema preparation process is outside the application's execution scope.

## 6. Database Identity and Privilege Management

Clearly distinguish application users from PostgreSQL database roles.

Use the following conceptual database identities:

| PostgreSQL role | Purpose |
|---|---|
| db_owner | Database object ownership and controlled administration |
| app_readonly | Read-only application operations |
| app_writer | Limited application write operations |
| app_vulnerable | Deliberately overprivileged experimental identity |
| auditor | Authorized security inspection |
| migration_role | Controlled schema migrations, outside normal application execution |

Important requirements:

- Never use PostgreSQL superuser credentials for normal application operations.
- Never expose database credentials to the frontend.
- Use least-privilege database access in Secure Mode.
- Keep vulnerable database identities separate from secure application identities.
- The overprivileged identity must not be an administrator or PostgreSQL superuser.
- Document the permissions required by each identity.
- Do not silently switch database identities between application requests.

The vulnerable identity must only be used in the isolated training environment.

## 11. Four Primary Security Experiments

The application must support the following controlled research scenarios.

### Scenario 1 — SQL Injection

Research objective:

Determine whether unsafe SQL query construction allows an attacker to manipulate the application's intended database operations.

Experimental variants:

- Variant A: Unsafe SQL string construction.
- Variant B: Parameterized SQL queries.

Defensive measures:

- Prepared statements.
- Parameterized queries.
- Safe database access patterns.
- Restricted application database identity.
- Input validation as supplementary protection.

Measurements:

- Unauthorized records accessed.
- Whether SQL query semantics were manipulated.
- Database role used.
- Corresponding application logs.
- Corresponding database logs.
- Whether the same test succeeds after remediation.

### Scenario 2 — Excessive Database Privileges

Research objective:

Determine whether an application database identity can perform operations beyond its assigned responsibilities.

Experimental variants:

- Variant A: Excessively privileged experimental account.
- Variant B: Least-privileged application account.

Defensive measures:

- Role separation.
- Explicit GRANT and REVOKE permissions.
- Restricted ownership.
- Separation of runtime and migration identities.
- PostgreSQL privilege auditing.

Measurements:

- Number of permitted operations.
- Unauthorized operations attempted.
- Unauthorized operations successfully performed.
- Difference between privilege configurations.

### Scenario 3 — Broken Authorization

Research objective:

Determine whether one customer can access another customer's financial resources.

Experimental variants:

- Variant A: Missing or incorrect ownership checks.
- Variant B: Correct server-side authorization.
- Variant C: PostgreSQL Row-Level Security.

Compare:

- Application-enforced access control.
- Database-enforced row-level access control.
- Combined application and database enforcement.

Important RLS considerations:

- Establish the correct database identity or trusted session context.
- Prevent users from manipulating authorization context.
- Ensure application connection pooling does not leak session-specific security state.
- Test both read and write operations.
- Verify RLS behavior using the actual application database roles.

Measurements:

- Cross-customer access attempts.
- Unauthorized records returned.
- Unauthorized modifications.
- Enforcement behavior at the application layer.
- Enforcement behavior at the database layer.

### Scenario 4 — Database Network Exposure

Research objective:

Determine whether PostgreSQL accepts connections from unauthorized network locations.

Experimental variants:

- Variant A: Database access restricted to the application VM.
- Variant B: Database unnecessarily exposed to the audit network.

Defensive measures:

- Network segmentation.
- Host firewall.
- PostgreSQL listener restrictions.
- PostgreSQL client authentication rules.
- TLS for database connections.

Measurements:

- Port accessibility.
- Connection success or failure.
- Source network.
- Authentication outcome.
- Evidence of permitted and denied connections.

Only perform network exposure experiments within the isolated VirtualBox laboratory.

## 12. Vulnerability Chaining

Support an additional experimental investigation of how multiple weaknesses can combine.

Illustrative attack chain:

1. Initial access through an application weakness.
2. SQL Injection.
3. Access through an excessively privileged database identity.
4. Unauthorized access to synthetic financial records.
5. Evidence collection and impact assessment.

Treat this as a conceptual attack path until each stage has been independently validated.

The research must answer:

- Does SQL Injection alone expose data?
- Does excessive privilege alone create unauthorized capabilities?
- Does combining both increase the demonstrated impact?
- Which individual defensive control breaks the chain?
- Do multiple defensive controls provide additional protection?

Record each experiment independently before combining vulnerabilities.

## 18. Research Methodology and Evaluation

1. Document the research objective.
2. Define the vulnerable configuration.
3. Execute the authorized test.
4. Record observations.
5. Collect application and database evidence.
6. Apply defensive controls.
7. Repeat the same test.
8. Compare the results.
9. Explain the security improvement.

- MITRE ATT&CK for observed attack techniques.

- CVSS 4.0 for independently justified severity assessment.
- OWASP guidance for application security.
- NIST guidance for security assessment methodology.

Do not invent experimental results, CVSS scores, or successful attacks.

Clearly distinguish expected results from experimentally observed results.

## 20. Development Instructions

Follow these implementation principles:

**First: Inspect before implementing.**

Understand the existing PostgreSQL database structure and the target deployment environment before writing database integration code.

Do not assume the database schema or modify it.

**Second: Build the functional application.**

Implement frontend/backend communication, authentication, database integration, and the financial dashboard.

**Third: Implement Secure Mode first.**

Ensure the normal financial application uses secure authentication, parameterized queries, least-privilege access, and server-side authorization.

**Fourth: Implement Vulnerable Lab Mode separately.**

Create isolated experimental implementations for the four research scenarios.

**Fifth: Implement the Security Lab interface.**

Display actual experiment configurations, execution status, evidence, and results.

**Sixth: Test everything.**

Verify frontend functionality, backend APIs, database connectivity, authorization, and security controls.

**Seventh: Document all important implementation decisions.**

Explain where configuration changes are required, how to execute experiments, and how to maintain the project.

### Additional implementation rules

- Do not create fake functionality or non-working buttons.
- Do not replace real database integration with hardcoded mock data.
- Do not invent database tables or columns.
- Do not automatically modify the existing database.
- Do not mix vulnerable and secure code paths.
- Do not expose sensitive information.
- Keep the code modular and maintainable.
- Handle errors properly.
- Include meaningful comments for security-critical logic.
- Include unit and integration tests.
- Explain all required environment variables.
- Document any assumptions or missing dependencies.
- If a requested feature cannot be implemented because of an external dependency, explain exactly what is missing rather than silently simulating it.

**Final objective:**

Build Borsa as a professional, functional financial web application and a reproducible cybersecurity research platform.

The result must combine a realistic user experience with a technically rigorous database security assessment environment, allowing researchers to demonstrate vulnerabilities, apply defensive controls, collect evidence, and quantitatively evaluate security improvements within an isolated three-VM laboratory.
